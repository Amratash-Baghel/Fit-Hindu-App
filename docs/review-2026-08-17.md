## 1. What was wrong, and is now fixed

### 1.1 A logged set could vanish from the offline queue (data loss) — FIXED
`src/lib/session.ts` · `flushQueue()`

`flushQueue` read the durable queue once into a local snapshot, then wrote that
snapshot back after each send. A set logged **while a send was in flight** was
appended to the stored queue by `enqueue`, and the next snapshot write erased it.
On the target device that window is a 2G round-trip — seconds — and taps do not
wait for it.

Why it mattered: the lost op is the only durable record of that set. The local
mirror holds it, but close-out re-queues the *finish* row and the activity row,
never the sets — so the set would be training the server never hears about,
which is precisely the loss this module exists to prevent.

Fix: the two post-send edits now re-read the queue **inside the existing serial
lock** and drop `n` from the head (`dropHead`) or bump the head's attempt count
(`penaliseHead`). Ops are only ever appended at the tail, so a head-relative
edit is always correct, and anything enqueued mid-send survives and is sent in
the same drain.

### 1.2 Admin: "+ New exercise" could fail on a duplicate slug — FIXED
`admin/app/(panel)/library/exercises/page.tsx` · `admin/components/NewEntityButton.tsx`

The slug was built as `` `exercise-${Date.now()}` `` **during render** of a
server component. Two effects: it was the one lint error in the repo
(`react-hooks/purity`, so `npx eslint .` in `admin/` was red), and the timestamp
was frozen into the rendered page — creating two exercises without a reload sent
the same slug twice, and `exercises.slug` is `unique`, so the second insert
failed with an alert. `NewEntityButton` now takes `slugPrefix` and stamps the
timestamp at click time.

### 1.3 Admin: the new Sort field rewrote itself mid-edit — FIXED
`admin/components/WorkoutComposer.tsx`

Found by `/code-review` on the slice-E diff: clearing the field to retype
snapped it back to 100. It now holds empty while editing and writes the 100
default on save (the column is `NOT NULL`).

### 1.4 26 dead i18n strings removed — FIXED
`src/lib/i18n.tsx`

`tab_jap`, `tab_sleep`, `start`, `pick_area`, `todays_workout`, `todays_diet`,
`todays_meditation`, `todays_jap`, `q_deity`, `q_deity_hint`, `deity_error`,
`onboarding_saving`, `auth_saved`, `delete_word` and 12 `progress_*` keys left
behind by the BMS/UI9 rewrites. `StringKey = keyof typeof strings` means a
still-referenced key would have failed `tsc` — typecheck is green, which is the
proof the removal was safe. Catalog: 381 → 355 pairs.

### 1.5 `@expo/ngrok` moved to devDependencies — FIXED
A dev-only tunnel helper for `expo start --tunnel` sat in runtime
`dependencies`. It is not bundled (nothing imports it), so this is hygiene and
supply-chain surface, not size.

## 2. Verified healthy (checked, no action needed)

- **RLS coverage is complete.** 33 tables created across the migrations, 33
  `enable row level security` statements. Every `security definer` function is
  deliberate and commented; the aggregate RPCs (`points_summary`,
  `progress_summary`, `streak_state`, `plan_progress`, `push_claim`'s readers)
  are `stable` and *not* definer, so the caller's RLS is the boundary.
- **No service-role key anywhere in the app or the panel.** The only
  `SUPABASE_SERVICE_ROLE_KEY` reader is `supabase/functions/send-push`, where
  the platform injects it. The push endpoint takes its recipient from the
  verified JWT (never the body), restricts client-triggerable kinds to
  `plan_ready`, gates cron kinds behind `CRON_SECRET`, and claims the day before
  sending. No send path exists in the client.
- **Live-database drift: none except the expected one.** Probed the live project
  (read-only, anon key): every table 0001–0020 exists, and `points_rules` /
  `streak_milestones` match the repo's 0020 column-for-column. **Only 0021 is
  unapplied** — confirmed by the exact error the app's fallback keys on
  (`42703 column workout_templates.sort does not exist`). This is the drift class
  that bit us on 0019, so it is worth re-probing after any long gap.
- **Timers and subscriptions all clean up.** Every `setInterval`/`setTimeout` in
  the app (sleep countdown + heartbeat, session player tick, meditation tick and
  ambient dim, verify cooldown, diet poll, splash sequences, tab-glow nav) is
  cleared in its effect teardown or a ref-tracked list.
- **`expo-dev-client` costs nothing in production.** Its heavy dependencies
  (dev-menu, manifests, Compose, okhttp, kotlin-reflect) are wired `debugOnly`
  in `expo-dev-launcher/android/build.gradle`, added to release only when a dev
  client is *built* in release mode. Keeping it in `dependencies` is correct.
- **No health-claim language in the string catalog**, no hardcoded deity or
  product in code (one comment in `BodyModel.tsx` cites the old site as visual
  inspiration), no `TODO`/`FIXME` debt markers, and exactly one `console.warn`
  in app code (the missing-env guard in `src/lib/supabase.ts`).

## 3. Worth fixing next (not touched in this pass)

Ranked by what they'd cost a real user.

1. **Meditation / jap / sleep / diet completions are not durable.** They call
   `logActivity()`, a single insert with no retry and no queue, while a workout
   goes through `session.ts`'s durable queue. Finish a sit on a dead connection
   and the streak row is simply lost — the same failure the workout path was
   rebuilt to eliminate. Fix shape: let the other four completions enqueue an
   `activity` op through the existing queue (it already carries a
   `client_event_id`, so replays collapse).
2. **`logActivity()` never stamps `program_id`,** while `session.ts`'s queued
   activity row does. Nothing filters on it today, so nothing is visibly broken
   — but the platform rule is that everything is program-scoped, and the day a
   report groups by program, four of five activity types will be unscoped
   history.
3. **`app/diet/plan.tsx` polls forever.** A pending/generating request is polled
   every 4 s with no cap and no backoff, so a screen left open on a stuck n8n run
   polls until the app is backgrounded. Suggest: stop after ~5 minutes and show a
   Refresh affordance.
4. **`t()` throws on an unknown key** (`strings[k].en` on `undefined`). Literal
   keys are type-checked, so this is unreachable from TypeScript — except through
   the `` t(`pillar_${k}` as StringKey) `` casts on Home and My Path. A
   `strings[k] ?? { hi: k, en: k }` fallback turns a future typo into an ugly
   label instead of a white screen.
5. **RN-web deprecation warnings** (`shadow*`, `textShadow*`,
   `props.pointerEvents`) fire on every screen in the preview. Harmless on web
   today, but they are the same props RN is migrating natively; a sweep in
   `src/ui/tokens.ts` + the few call sites clears the console for good.
6. **`expo` 57.0.12 → 57.0.14 and 6 packages want aligning**
   (`npx expo install --check`). Worth doing *before* the next EAS build, not
   between one and its smoke test.

## 4. App size: measurements, estimate, and the levers

### 4.1 What is measured (real numbers from this repo)

`npx expo export --platform android` on the current tree:

| Piece | Size |
| --- | --- |
| Hermes bytecode bundle (`.hbc`) | **4.8 MB** |
| Bundled assets (icons, fonts, audio, nav art) | **1.7 MB** |
| **Total JS + asset payload** | **6.5 MB** |

Repo assets, for context: `icon.png` 385 KB, `assets/audio` 562 KB (om chant +
flute loops), `assets/sfx` 92 KB (4 WAVs). Video and sleep audio stay on the
CDN by standing rule, so content growth does **not** grow the binary.

### 4.2 What cannot be measured here

There is no Android SDK and no JRE on this machine, and the project is managed
(no `android/` folder), so an APK cannot be built locally — the native half has
to be estimated. After the exclusion in §4.4 there are **25 autolinked native
modules**; the weight is dominated by React Native + Hermes, the ExoPlayer/media3
stack behind `expo-video`/`expo-audio`, Reanimated + worklets, and
`react-native-screens`/`svg`.

### 4.3 Estimate against the target

| Artifact | Expected | Verdict vs. 100 MB cap |
| --- | --- | --- |
| AAB → Play install on an arm64 phone | **~55–75 MB** | inside the 50–70 MB expectation |
| AAB → Play *download* | ~20–30 MB | comfortable |
| Single-ABI (arm64) release APK | ~30–45 MB | comfortable |
| **Universal APK (4 ABIs), no shrinking** | **~70–110 MB** | **the one way to breach the cap** |

Read that last row as the action item: the cap is a *packaging* risk, not a code
risk. Nothing in the app's own payload (6.5 MB) threatens it.

### 4.4 Levers, in order of value

1. **Ship the AAB to Play** (EAS `production` default). Play splits per ABI, so
   the four-architecture problem disappears for real users.
2. **For hand-shared demo APKs, restrict the ABIs.** A universal APK is the
   worst case above; arm64-only covers every phone worth demoing on. Via
   `expo-build-properties`:
   ```json
   ["expo-build-properties", { "android": { "abiFilters": ["arm64-v8a"] } }]
   ```
   (add `"armeabi-v7a"` only if a genuinely old handset must run it).
3. **Enable R8 + resource shrinking for release** — typically 3–8 MB off dex:
   ```json
   ["expo-build-properties", {
     "android": {
       "enableProguardInReleaseBuilds": true,
       "enableShrinkResourcesInReleaseBuilds": true
     }
   }]
   ```
   Deliberately *not* applied in this pass: it changes the native build and
   cannot be verified without one, so it wants a build + a click-through, not an
   unattended commit.
4. **Done in this pass — dropped two unused native modules** from autolinking:
   ```json
   "expo": { "autolinking": { "exclude": ["@expo/ui", "@expo/dom-webview"] } }
   ```
   Both ship inside the `expo` package and link by default; nothing in this app
   imports either. `@expo/ui` alone is a 1.9 MB AAR that drags in Jetpack
   Compose; `@expo/dom-webview` pulls `androidx.webview`. Verified with
   `expo-modules-autolinking resolve -p android`: 27 → 25 modules. **The next
   EAS build must be smoke-tested** — that is the only way to confirm a native
   exclusion, and reverting is a one-line edit.
5. **Minor:** `icon.png` is 385 KB for a 1024² PNG that compresses to ~40 KB.
   Worth a pass whenever the brand assets are next touched.
